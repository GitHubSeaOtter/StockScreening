# model-routing: フェーズ分解とモデル割当

model-routing スキルの方針(タスクをフェーズ分解し、品質基準を満たす
最もコスト効率の良いモデルを各フェーズに割り当てる)に基づく記録。

## フェーズ分解

| フェーズ | 内容 | 割当 | 理由 |
|---|---|---|---|
| 設計・実装 | 要件解釈・アーキテクチャ・条件エンジン | 開発セッションの最上位モデル | 設計判断と仕様の曖昧さ解消に知能が必要 |
| データ生成(GitHub Actions) | 銘柄取得・特徴量計算 | **LLM 不使用** | 決定論的な数値計算。LLM を使う理由がなくコストゼロ |
| 条件評価(ブラウザ) | 特徴量ベクトルへの条件適用 | **LLM 不使用** | 同上。Python↔JS の parity テストで正しさを担保 |
| 自然言語→条件変換(任意) | 日本語の条件文 → 構造化 JSON | **claude-haiku-4-5** | 下記参照 |

## ランタイム LLM の選定理由

- タスクは「短い日本語文 → 固定スキーマの JSON 抽出」という Haiku 級のタスク。
  構造化出力(`output_config.format` の json_schema, enum 制約)でスキーマ準拠が
  API レベルで保証されるため、上位モデルとの品質差がほぼ消える。
- 料金比較(入力/出力 $/1M トークン):
  - claude-haiku-4-5: **$1 / $5** ← 採用
  - claude-sonnet-5: $3 / $15
  - claude-opus-4-8: $5 / $25
- 1 回の変換は入力 ~600 + 出力 ~150 トークンで **約 $0.001**。ユーザー体感では実質無料。

## 弱いモデルへの補償(handoff spec)

Haiku に渡すシステムプロンプトに以下を織り込み、モデルの弱さを仕様の厳密さで補う:

- 条件タイプ 5 種の意味と各フィールドの定義を全列挙
- json_schema(enum 制約付き)で出力形状を強制
- 「解釈できない要素は無視し、確実に読み取れた条件のみ出力」というフェイルセーフ指示

localStorage にのみ保存し、リポジトリや共有サーバーには一切保存しない。
