# model-routing: フェーズ分解とモデル割当

model-routing スキルの方針(タスクをフェーズ分解し、品質基準を満たす
最もコスト効率の良いモデルを各フェーズに割り当てる)に基づく記録。

## フェーズ分解

| フェーズ | 内容 | 割当 | 理由 |
|---|---|---|---|
| 設計 | 要件解釈・アーキテクチャ・条件エンジン設計 | 開発セッションの最上位モデル | 仕様の曖昧さ解消と設計判断は最も知能が必要 |
| 実装 | バックエンド + モバイル UI + テスト | 同一セッション内で直接実装 | サブエージェント分割はコンテキスト再構築コストが上回る |
| ランタイム(スクリーニング) | 条件評価・騰落率計算 | **LLM 不使用** | 決定論的な数値計算。LLM を使う理由がなく、コストはゼロ |
| ランタイム(自然言語→条件変換) | 日本語の条件文 → 構造化 JSON | **claude-haiku-4-5** | 下記参照 |

## ランタイム LLM の選定理由

- タスクは「短い日本語文 → 固定スキーマの JSON 抽出」という Haiku 級のタスク。
  構造化出力(`output_config.format` の json_schema)でスキーマ準拠が API レベルで
  保証されるため、上位モデルとの品質差がほぼ消える。
- 料金比較(2026-06 時点、入力/出力 $/1M トークン):
  - claude-haiku-4-5: **$1 / $5** ← 採用
  - claude-sonnet-5: $3 / $15
  - claude-opus-4-8: $5 / $25
- 1 回の変換は入力 ~600 トークン(システムプロンプト含む)+ 出力 ~150 トークンで
  **1 回あたり約 $0.001**。ユーザー体感では実質無料。

## 弱いモデルへの補償(handoff spec)

Haiku に渡すシステムプロンプトに以下を織り込み、モデルの弱さを仕様の厳密さで補う:

- 条件タイプ 5 種の意味と各フィールドの定義を全て列挙
- json_schema(enum 制約付き)で出力形状を強制
- 「解釈できない要素は無視し、確実に読み取れた条件のみ出力」というフェイルセーフ指示

## API キーの扱い

`config/settings.json`(gitignore 済み)にローカル保存。キー未設定でも
スクリーニング本体は全機能動作する(LLM は完全にオプショナル)。
