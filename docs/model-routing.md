# model-routing: フェーズ分解とモデル割当

model-routing スキルの方針(タスクをフェーズ分解し、品質基準を満たす
最もコスト効率の良いモデルを各フェーズに割り当てる)に基づく記録。

## フェーズ分解

| フェーズ | 内容 | 割当 | 理由 |
|---|---|---|---|
| 設計・実装 | 要件解釈・アーキテクチャ・条件エンジン | 開発セッションの最上位モデル | 設計判断と仕様の曖昧さ解消に知能が必要 |
| データ生成(GitHub Actions) | 銘柄取得・特徴量計算 | **LLM 不使用** | 決定論的な数値計算。LLM を使う理由がなくコストゼロ |
| 条件評価(ブラウザ) | 特徴量ベクトルへの条件適用 | **LLM 不使用** | 同上。Python↔JS の parity テストで正しさを担保 |
| 自然言語→条件変換(任意) | 日本語の条件文 → 構造化 JSON | **gpt-4.1-mini / claude-haiku-4-5** | ユーザーが API プロバイダーを選択 |

## ランタイム LLM の選定理由

- 短い条件文を固定スキーマに変換するため、軽量モデルを使用する。
- 両プロバイダーで JSON schema を使い、画面側でも数値範囲と列挙値を検証する。
- 市場と時間外価格の選択を条件と一緒に解釈する。

## 弱いモデルへの補償(handoff spec)

両モデルに渡すシステムプロンプトに以下を含める:

- 週・月の連続騰落を含む条件タイプの意味と各フィールドの定義を全列挙
- json_schema(enum 制約付き)で出力形状を強制
- 表現できない条件は `unhandled` に返し、画面に表示して部分的な結果を出さない

## API キーの扱い(GitHub Pages 静的サイト構成)

サーバーを持たないため、変換はブラウザから選択した API を直接呼び出す。
OpenAI は Responses API と JSON schema に統一する。
API キーは端末の localStorage にのみ保存し、リポジトリや共有サーバーには保存しない。
キー未設定でも、手動の条件指定でスクリーニングは全機能動作する(LLM は完全にオプショナル)。
